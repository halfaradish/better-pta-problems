# 自动答题初探（2026-10-12 内置浏览器实测）

> 目标：为「配置 LLM → 开始答题 → 作答并保存（选择/填空/判断）」功能积累流程经验。本轮只探索不写代码。
> 实测对象：`2100000000000000010`（课堂练习2-1：判断 5 题 + 单选 10 题）、`2100000000000000011`（课堂练习1-5：判断 10 + 单选 5 + 填空 5）。

## 1. 页面结构与路由

- 答题页 URL 形状：`/problem-sets/{problemSetId}/exam/problems/type/{n}`，`n` = 题型：1=TRUE_OR_FALSE（判断）、2=MULTIPLE_CHOICE（单选）、4=FILL_IN_THE_BLANK（填空）。
- **一个题型页把该题型全部题目平铺在一页**（无分页，「当前1 - 10项，共10项」是静态文案）。
- 左侧题目总览（答题卡）：每题型一行「判断题 5/5」格式 = 已作答/总数；每题一个数字链接，实心（已答）/虚线框（未答）。
- 每题容器的 `id` 就是 `problemSetProblemId`（雪花 ID 字符串，纯数字），按 `type` 页内题号顺序连续递增（如 21000000000000010437–2446）。
- 单题 deep-link：`.../exam/problems/type/2?problemSetProblemId={id}`，可用于滚动定位（容器同时有 `scroll-mt-0`）。
- 每题头部信息：题号（"2-3"按钮）、分数、作者、单位；题干在 `p` 标签内，可能内嵌富文本（`rendered-markdown`）：代码块（带 复制/格式/全屏 按钮）、`O(logn)` 上标等 → **LLM 读题需要取渲染后的纯文本而不是原始 markdown**。
- 页面顶部：题型页签（判断/单选/填空）、剩余时间徽标（"6 天"）、状态"答题中"；底部固定「保存」按钮（`pc-button`）。
- 侧栏底部导航：概览 `/exam/overview`（答题信息+进度表）、题目列表、提交列表 `/exam/submissions`、排名。

## 2. 表单 DOM（可直接自动化的形状）

| 题型 | 元素 | name | value | 选中态 |
|---|---|---|---|---|
| 单选 | `input[type=radio]` ×4（A/B/C/D 各一个） | `=题容器id`（problemSetProblemId） | 恒为 `"on"` | `checked` |
| 判断 | `input[type=radio]` ×2 | 同上 | `"on"` | `checked`；**DOM 顺序 = [T, F]** |
| 填空 | `input[type=text]`（每空一个，一题可多空） | — | 输入值 | `value` |

- 选项的字母与文本在 radio 的 `label` 中（`label.textContent` ≈ "C.问题规模不同，问题性质相同"）；文本区在 `p` 标签。
- 选项文字随 PTA 的浅/深主题有 `rendered-markdown` 包裹，判定"选项顺序"只能靠 DOM 顺序/label 字母前缀，不要靠颜色。

## 3. 数据请求（读题数据从哪来）

页面加载时发出（全部 XHR，**响应为 `application/x-protobuf`**，非 JSON）：

| 接口 | 作用 |
|---|---|
| `GET /api/problem-sets/{psId}/exams` | 取 authKey / examId |
| `GET /api/problem-sets/{psId}/problem-summaries` | 各题型 总数/总分（未答/已答统计） |
| `GET /api/exams/{examId}/problem-sets/{psId}/problem-status` | 每题作答状态（扩展 v0.8 已用） |
| `GET /api/problem-sets/{psId}/exam-problems?exam_id={examId}&problem_type={TYPE}` | **完整题目数据（题干+选项+已保存答案），protobuf** |
| `GET /api/problem-sets/{psId}/standard-answers?problem_type={TYPE}` | 标准答案（答题中状态下响应体为空，考试结束后才有内容）——**答题中拿不到答案** |
| `GET /api/exams/{examId}/problem-sets/{psId}/last-submissions?problem_type={TYPE}` | 已提交/判分记录 |
| `GET /api/user-storage/names/answerSettings` | 用户偏好 |

- React 树里能直接读到（同 protobuf 的直读替代）：`problemSetId / activeProblemType / problemPoolIndex / problemSubmissionStatus("PROBLEM_SUBMITTED") / 分数`；题目集类型 `type: "EXERCISE"`。
- protobuf 解析成本高；**自动化更省事的是读 DOM**（题干文本 + radio/label 已足够组装 LLM prompt）。

## 4. 保存（提交）协议 — 实测确认

入口只有一个：页面底部「保存」按钮。点击后对**当前页面上有 checked/填值的题**发一批请求（每题型一次 POST）：

```
POST /api/exams/{examId}/exam-submissions
Content-Type: application/json
{ TS: 1791818449007, LT: {...}, x-csrf-token: "f43a5503-83d2-497f-8867-4bbf1c9b1347" }  // headers 由页面自动带
```

请求体按题型分 `problemType` + `details`（一次请求只含一种题型）：

```json
// 单选
{"problemType":"MULTIPLE_CHOICE","details":[
  {"problemSetProblemId":"21000000000000010437","multipleChoiceSubmissionDetail":{"answer":"C"},"problemId":"0"},
  {"problemSetProblemId":"21000000000000010438","multipleChoiceSubmissionDetail":{"answer":"D"},"problemId":"0"},
  {"problemSetProblemId":"21000000000000010439","multipleChoiceSubmissionDetail":{"answer":"C"}}]}

// 判断
{"problemType":"TRUE_OR_FALSE","details":[
  {"problemId":"0","problemSetProblemId":"21000000000000020768","trueOrFalseSubmissionDetail":{"answer":"TRUE"}}]}

// 填空（每空一条，answers 数组按空序）
{"problemType":"FILL_IN_THE_BLANK","details":[
  {"problemId":"0","problemSetProblemId":"21000000000000020786","fillInTheBlankSubmissionDetail":{"answers":["n"]}}]}
```

- `answer: "C"` 用**选项字母**（单选）或 `"TRUE"/"FALSE"`（判断）——与 UI 展示的字母/字面一致。
- `problemId` 恒为 `"0"`（占位，可不带）。
- 点「保存」前，radio/输入框的改动**只存在前端内存**（曾观察：点击选项后 0 网络请求），保存按钮才触发 POST → 天然适合「全部答完→一次保存」的自动化流。
- POST 成功后页面自动 GET `last-submissions` 刷新状态；无误弹窗（实测一次保存成功未出现任何 confirm/toast 阻塞）。
- 每次保存产生一条新的 submission（可重新保存=覆盖，历史记录显示"已被覆盖"）。

## 5. 判分与反馈

- 这些题目集（老师设置 `hasGrading:false` / EXERCISE 类型）**答题中不判分**：提交详情页明示「此题型将在考试结束后统一评测」，状态一直"等待评测"。
- 因此答题中**页面上每题不会显示对错**（无 ✓/✗ 图标、无"回答正确"文案、无解析）；已保存的答案只表现为 radio 回显 checked + 答题卡数字变实心。
- `standard-answers` 接口在答题中响应体为空（`content-type: protobuf` 但无内容）→ **自动答题期间的正确性无法从平台反馈中学习，完全依赖 LLM 自身**。
- 提交详情页表格：单选 `2-3 / C / - / 2`；填空 `填空# / 答案 / 结果 / 得分`；判分后这里有对错与得分，**但没有"正确答案"列**（只有你的答案）。
- 概览页有答题进度表（题型× 已作答/总题数×%）和剩余时间，可用来做"无缝续答"。

## 6. 对「LLM 自动答题」的流程启示

1. **读题**：DOM 路径最稳——每题容器 `[id=problemSetProblemId]` 下的 `innerText` 已含题号/分值/题干/选项字母+文本；多空填空题要按 `input[type=text]` 在容器内的出现顺序对应 `answers[]` 下标。
2. **组 prompt**：单选给选项字母映射，判断固定 T/F 二选一（输出 TRUE/FALSE），填空输出数组（按空分隔）。注意公式以富文本形式出现（O(n²) 的上标在 `text`+`generic` 节点拼接），直接 `innerText` 即可得到读得懂的文本。
3. **写答案**：radio 用真实点击（React 受控组件要触发原生 input 事件链；实测 Playwright `click()` 即可触发）；填空 `input` 用 native value setter + `input`/`change` 事件。
4. **保存**：全题型答完后点一次「保存」即可（产生一次每题型一条的 exam-submissions POST）。或者按题复用同协议直接发 POST（headers 由页面上下文自动携带：`TS/LT/x-csrf-token`+登录态）。
5. **验证保存成功**：比较保存前后 `problem-status`/答题卡数字，或读 POST 响应码。
6. **重新保存**：安全（生成新 submission 覆盖），但判分为"考试结束后统一评测"，中途反复改答案没有即时对错反馈可校准 —— 依赖 LLM 单次质量。
7. 反爬/行为风控面：本轮未见验证码或限流；保存属用户主动行为频率，自动化应保持人类操作节奏（保存间隔秒级）避免可疑。

## 7.1 补充实测（2026-10-12 第二轮）：图片题、代码块题、已判分题集

> 针对两个新样本验证既有结论是否成立：`2100000000000000012`（数据结构复习题(图)，**已关闭且已判分**，25 题单选，多图表题）、`2100000000000000010` 的 2-7（CodeMirror 代码块题）。

**图片题/图片选项（图复习题集）**

- 图片一律 `<img src="https://images.ptausercontent.com/{id}">`，`alt` 基本为空；区分数字型 id（`/19`、`/267`——题库老图）与 UUID 文件名（`/eac326c4-….JPG`，alt 是上传时的文件名如 "Dij1.JPG"、"题图.jpg"）。
- 出现位置两类：①题干内（`inChoice=false`）：题干 markdown 里的插图，**此时 `innerText` 只会给文件名/空串，题面语义在图里**；②选项内（`inChoice=true`，在 `label` 里）：整个选项就是一张图（如"下列哪个图不可能对应该 DFS 序"），选项 label 的 innerText 只剩 "A."、"B."…，**纯文本 prompt 组不出选项语义**。
- 影响：这类题 LLM 文本链路失明，必须走**图片输入**（截图/底图 URL 下载后给视觉模型），或至少在 prompt 里标注"[选项 A 为图片]"并把图作为附件。URL 直接可带登录态下载（图片域与页面无关，无需特殊头）。本轮未见这题出现在将做的选择/填空/判断之外，但属于高频题型（图论复习题 25 题里 11 题带图），需要设计兜底。

**代码块题（2-7）**

- 代码块是 CodeMirror 6（`.cm-editor`，readOnly），带独立行号 gutter 与「复制内容/格式/全屏/收起」按钮。
- **裸 `innerText` 会被行号污染**：实测 2-7 容器 innerText 里有 `1\n2\n…\n13` 把代码行隔开（且按钮文字"复制内容/格式/全屏/收起"混入），LLM 直接读会看到大量噪音，但代码语义仍在，大模型通常也能拼回来——**更稳的做法是从 CodeMirror 实例取纯文本**：`.cm-content` DOM 对象上挂的 `cmView.view.state.doc.toString()` 直接返回干净代码（实测拿到完整 13 行，无行号）。
- 「复制内容」点击后写剪贴板（IAB 里页面自己读剪贴板被拒，但作为人机交互正常）；自动化走 `state.doc` 即可，无需模拟点击。
- 上下标公式（O(N^2) 的上标"2"）在 label innerText 里以换行拆开（"O(N | 2 | logN)"）——保留换行交给 LLM 理解即可，无需还原 mark-up。

**已关闭+已判分题集（图复习题集）**

- `standard-answers` 接口**关集后仍为空**（protobuf，0 字节）→ 平台不会把标准答案直接吐给前端，先前第 5 节"答题中拿不到答案"的结论在关集后同样成立。
- 判分后题卡会出现「评测结果 / 答案正确|答案错误 / 得分 X 分」区块（统计样本：15 对 10 错），但**不会标出正确选项**（答错的我 View 了 2-3：无高亮、无 ✓/✗ 图标、radio 全部 disabled 锁定不可改）。
- 提交详情页判分后形如 `2-1 / B / 答案正确 / 4/4`……同样**只有你的答案没有正确答案**；「所有提交」里能看到全班的提交状态列表（tab=all）。
- 结论加强：对答案回收只能依赖**判分结果的离线归纳**（自己答的对错分布）或人工对答案，平台不会给正确答案明文；做"复盘学习"数据源时要基于判分正误而不是答案文本。
- 已关闭题集的表单全部 disabled、无保存按钮 → 已关闭的题集对自动化只读。

## 9. 方案决策与实现（v0.9.0，2026-10-13 更新）

**前端选型（第一版为弹窗承载，后按用户决定改为悬浮面板）：**

- 弹窗只留一个「自动答题面板」总开关（默认关）；题目列表页（/exam/problems…）出现**悬浮答题球**（固定右下、品牌蓝渐变、「答」字标），点开为悬浮面板。
- 面板以 Shadow DOM 隔离（不吸 PTA 样式、不外泄类名），设计令牌与设置弹窗同源（#0a4991 品牌蓝、明暗双主题 follow prefers-color-scheme、600px 上限不再适用于页面内面板）。
- 面板内容：模型适配选择（DeepSeek = 官方 api.deepseek.com / deepseek-flash 固定，视觉模型——deepseek-chat 已下架，2026-10-13 换用；OpenCode Go = Zen Go 网关 opencode.ai/zen/go/v1，默认 glm-5.3-flash，选中后多一行「模型」可自填，只放行 /chat/completions 协议的模型系——glm/kimi/deepseek 可用，claude/minimax 走 /messages、grok/gpt 系走 /responses 暂不解析；网关要求 x-opencode-session 会话头与自建 UA，引擎按预设 gateway 条件附加；**v0.11.1 修正：基址改为官方口径 `opencode.ai/inference/go/openai/v1`；网关不返回 CORS 头（预检 404），页面直连在真机不可用，改由 background 转发；浏览器禁止脚本设置 User-Agent，实际使用浏览器自身 UA；非 chat 系模型在开跑前按前缀拒绝**）→ API Key（密码框 + 显隐切换，仅存本机扩展存储）→ 覆盖已作答开关 → 开始答题（进度胶囊 + 进度环）→ 日志（时间戳 + 级别配色 ✓/✕/!，可清空，role=log，上限 200 行）。服务/模型选择持久化为 autoAnswerGateway / autoAnswerModel / autoAnswerBaseUrl（纯增量默认值，不 bump settingsVersion）。第三项「自定义」= 自填任意 OpenAI 兼容端点 + 模型 id（端点走 normalizeBaseUrl 规整：去空白/尾斜杠，误粘完整 /chat/completions 自动剥掉再拼回，自定义不加网关头）。注意：引擎的图片输入只接在客观题上（「作答含图题」开关，默认跳过）；编程题没有视觉链路，v0.11.2 起含图题不再跳过，按文字题面作答并在日志注明「编程题暂不支持图片输入」。
- 引擎事件流 `setEventSink`：log/progress/state 三种事件；**完成事件必须在 running 复位之后发**，否则面板收不到结束态（事故一）。

**已定不变的部分：** 单选/判断/填空三题型（多空支持）；已答默认跳过、开关可覆盖；含图题跳过并报告（客观题；编程题自 v0.11.2 起按文字题面作答）；一次运行遍历全部题型页；每题独立请求（并发 3、重试 1 次、温度 0、JSON 输出）；点原生「保存」按钮并以 exam-submissions 请求为成功依据；运行在内容脚本、关弹窗/收面板不打断；被导航离开只读中止。

**关键事故与护栏（写代码的人必须记住）：**

- **mock LLM 走过一次真实保存路径**，把课堂练习 2-1（2100000000000000010，examId 9000000000000000001）的 15 个答案覆盖成 mock（判断全 TRUE、单选全 C）。引擎护栏已加：`handleRun` 检测到 `globalThis.__BPS_LLM_MOCK__` 且未显式 drySave 时强制 dry run 并告警——**任何时候用 mock 验证都必须 dry**。
- 恢复靠 PTA 自身接口（同一登录态 fetch，带 `accept: application/json` 即得 JSON）：提交列表 `GET /api/exams/{examId}/problem-sets/{psId}/user-submissions?limit=50&filter={}`；提交详情 `GET /api/submissions/{submissionId}`（submissionDetails 内 multipleChoiceSubmissionDetail.answer / trueOrFalseSubmissionDetail.answer / fillInTheBlankSubmissionDetail.answers）。用户答案被覆盖不等于丢失——OVERRIDDEN 状态的旧提交详情仍在，把答案重填重存即可还原（已还原并反查确认）。
- 教训二：**恢复/重填必须在页面完全水合后点击**（等作答态两次探测指纹一致）；数据早到的重渲染会把早点的选择丢掉（事故二，判断题恰好通过、单选第一次落了 空 C 但后续补救成功）。

**真机回归（IAB 注入产物，悬浮面板版）：** 开关关→球不出现；开→题目页出现球；点球展开面板（模型下拉 DeepSeek / OpenCode Go 可切换、切到后者多出「模型」自填行、密码框、开关、按钮、空日志）；空 Key 点开始→日志报错不运行；mock+覆盖（引擎强制 dry）：15 题逐条日志 `2-N → C`、进度环走满、结束态「已完成」、清空日志生效；弹窗折叠态 591px。单测 49 例。

### 10.1 页面形态与客观题的根本差异

- 题目详情 `GET /api/problem-sets/{psId}/exam-problems/{pspId}`：`problemSetProblem{problemConfig.programmingProblemConfig{timeLimit(200ms), memoryLimit(64MB), codeSizeLimit(16KB), cases{score…}}, title, type, compiler, description…}`——限制条件可以直接进 prompt。`solution` 字段存在但 `solutionVisible:false`，**不用平台答案，让模型自己做**。

- **collectPage 语义**：编程题页 `main [id]` 无题容器，`collectPage` 返回 0 题（`TYPE_BY_NAME` 未含「编程题」时引擎照旧跳过告警）——**行为保留**。编程题走 `collectProgramming()`：题干 = cleanText(main 去掉 CodingProblemAnswerForm 子树)；imgInfo 只记 stem 题干图（现在仅用于日志提示）；answered = cm 非空；langLabel = react-select 单值文本（经 normalizeLangLabel）。**编程题不接视觉链路**（取图与带图消息组装只做在客观题 `answerOne` 上）：含图题照常按文字题面作答并真实提交，日志写明「题干含图片，编程题暂不支持图片输入，仅按文字题面作答」；原先「未开『作答含图题』就整题跳过」的分支已移除（用户反馈：一般配图不影响 LLM 作答，跳过反而漏题）。
- **buildPrompt / parseCodeAnswer**：编程题输出是**围栏代码**（不是 JSON）——buildPrompt PROGRAMMING 分支：语言名嵌入输出行、要求围栏包裹、不打印任何 JSON 约束；parseCodeAnswer 解析优先「```lang\n代码```」整段（多围栏取最长），其次 JSON `{"answer": code}` 兜底（代码里的花括号贪婪匹配必炸，JSON 只能整串 parse），最后无围栏整串源码回退。
- **execCommand/全选路径的历史教训**：等待 PTA 内部状态同步靠「提交按钮 disabled 与否」（disabled=true 空码，false 非空）——水合后最多 3s 常见，但 execCommand 写入在隔离世界是**异步**的（水合失败后 PTA 自动草稿保存会把旧状态覆盖回来）。 Relay 方案彻底离开了 DOM 操作，避开这条 ces高 complexity 链路。

**干跑验证（IAB 真机 + 注入构建产物 + sessionStorage relay 副本，mock LLM+drySave：零提交、零草稿残留）**：

- dry10（单题）：失败复现为「水合校验失败」的头部代码预期只有 4 项，几乎都是 false mode：**execCommand 路线的彻底不可靠 + codingProblem 缓存未被清 + relayNext 未重置 phase/hint**。多项修复轮换后 dry16-18 单题与最后一拟题均 `ok:true`。
- dry18/dry18b：单题走通后 6 题接力（dry18 部分恢复 pi+1 起步；合抱 0528/231 两题走完整）——**全部六题 `ok:true`**，零提交零残留；dry15 类传输代驾本身还在 IAB 沙盒上偶发卡住（Ra той document reload 被 sandbox 阻挡），换「新标签页搬运」就稳了——**真实扩展没有这些沙盒限制**（location.href/整页 reload 都是浏览器标准行为），relayVer 验证以真扩展为准。
- 投产验证待做：真实扩展 key 含 deepseek-flash 或其他 OpenAI 兼容视觉/平和流 LLM 真跑（面板语言区读「本题允许的语言」+ 语言重设）。

**黑匣子**：`__BPS_AA_TRACE__`（40 条事件轮换存档 sessionStorage）+ `__BPS_AA_LAST_EVENT__`（末事件）+ `__BPS_AA_SUMMARY_DONE__`（收尾墓碑）——三处都在 sessionStorage，任何新页可读，relay 断线结算日志不会丢。

**探针证据存档**：apiReqs 出现 `/api/problem-sets/problems/{pspId}/exam-draft`、`/api/exams/{examId}/problem-sets/{psId}/last-submissions`、`/api/exams/{examId}/problem-sets/{psId}/exam-problems`…（页面自身请求）；bundle 在 main.*.js + a9fbe*.chunk.js，`createAPI` 注册表与 `programmingSubmissionDetail` 组装函数可复核。

### 10.7 水合机制变更与修复（2026-10-15 实机诊断，v0.9.5）

某实题集编程题 **4/4 全挂「水合校验失败（编辑器未回带代码）」**。实机诊断（IAB 新标签页真加载 + 探针草稿，全程零提交零残留）：

- **根因：PTA 前端更新后，编程题 boot 不再从服务端 `/exam-draft` 水合编辑器**。实测证据链：①DOM 契约未变（`CodingProblemAnswerForm` / 可编辑 `.cm-content` /「提交本题作答」按钮都在）；②按引擎同款请求体 POST 草稿 → 200 且持久（复 GET 回带 program + saveAt 已更新）＝写入侧没坏；③**服务端草稿有码的全新文档真加载** → 编辑器空、按钮 46s+ 不解锁，且 `PAT_HTTP_CACHE` 草稿条目始终 0 条＝**boot 连 exam-draft 的 GET 都不再发生**（该缓存只由 PTA 自家 fetch 包装层写入，条目数是「应用是否取数」的可靠旁证）；④编辑器内容现行数据源只剩 `codingProblem_{id}` 本地键（{program, testData, saveAt}，手敲立即落键；boot 不再自动把键存回服务端草稿——当日实测种键 boot 后服务端 saveAt 未变）。
- **引擎每题死法**：collect POST 草稿成功 + strip + clearCodingProblemCache + reload → verify 全新文档从（被删空的）键路径水合 = 空编辑器 → waitHydrate 20s 超时 → 报水合失败 + 回滚。注意该失败文案同时覆盖「按钮不解锁」与「head 不含」两分支，单看日志无法区分。
- **修复（seedCodingProblemCache）**：collect 写完服务端草稿后**种入** `codingProblem_{id}` 键（program=本题代码、testData=detail.customTestData.content、saveAt=当前 ISO——形状照抄 PTA 自写键）再 reload；种入失败当场记失败不翻页。`clearCodingProblemCache` 保留给 verify 撤销/提交失败回滚清键。服务端草稿写入照旧（提交/恢复链仍需要）。
- **修复的实证链**：①种键 → **全新标签页真加载** → 编辑器回带种入代码 + 按钮解锁，键在 boot 后仍在；②生产场景等价复刻：空编辑器活体文档种键 → 页内真 reload（新文档）→ 同样回带——**unload 前活体 SPA 未回写覆盖种入值**。verify 的 waitHydrate/语言守卫/提交逻辑不变。
- 诊断方法教训：IAB 的 `tab.reload()`/`tab.goto()` 会静默不发生真导航（window 标志位跨"刷新"存活、`performance.timeOrigin` 陈旧），验证「真加载后水合」必须开新标签页；用条目数判断应用是否 GET 过某接口，比猜缓存层更可靠。

### 10.8 LLM 卡死与后台通道（2026-10-23 真机故障，v0.11.3）

7-9/7-10 两题在 OpenCode Go 上分别报 `message channel closed` 与「请求 120s 无响应」，中间数分钟无日志。按时间戳反推：7-9 约 254s（两次 120s 超时后，第三轮约 11s 时后台通道关闭）、7-10 约 364s（三次 120s 超时），说明网关那段时间完全不回包；命令行用假 Key 探同端点 0.9s 返回 401（DNS 7ms / TCP 87ms / TLS 0.53s），排除网络、CORS 与请求体问题。教训与口径：

- **客户端超时是「总时长」时，分不清慢与死**：非流式响应要等整段生成完才有 body，要么等到超时，要么误杀长输出。改为 `stream: true` 后，**45s 无响应头/无数据**即可判定卡住，300s 总上限只兜住真正超长的生成；空闲超时最多重试一次，总超时不重试。网关忽略 `stream` 时按 `content-type` 退回整段 JSON。
- **「长时间没内容」不一定是死连接**：第三轮 7-9 的日志里 45s 空闲看门狗始终没触发（说明流持续有数据），但首个内容块直到 **174.6s** 才到，随后被 180s 总上限切断。这是模型长思考/网关排队，不是网关卡死。修复 = 总上限放宽到 **300s**，识别 `delta.reasoning_content` / `delta.reasoning` 记「模型思考中… 已收到 N 字符推理」，并新增 `stream`（流已建立）与 `stream-wait`（流开着但还没内容）进度，把「排队 / 思考 / 卡死」区分开；请求行同时标注模型名。
- **单条 `sendMessage` 不能横跨数分钟**：MV3 worker 被回收时，发送端只会得到 Chrome 的 `message channel closed` 文案，真实原因（网关超时）被覆盖。改为长连接端口 `bps-llm` 后，进度与结果分多条消息回传；断开事件显式可捕获并按可重试处理，页面关闭/中止时后台 `onDisconnect` 会取消在途 fetch。
- **端口模式下必须给 worker 保活**：改端口后的第二轮真机（7-9/7-10 每条尝试都恰好在 30.1–31.7s 断线）暴露了 MV3 的另一个边界——**挂起的 `fetch` 不算扩展活动**，等首块时既没有事件也没有 API 调用，worker 在 30s 空闲时被回收、端口随之关闭（旧的长消息模式靠挂起的 `sendResponse` 才活到 120s）。修复 = 等首块期间每 20s 调一次 `chrome.runtime.getPlatformInfo` 顶住 idle 计时器，同时回一条 `waiting` 进度（内容脚本记「仍在等待模型响应」）。无头 Edge 静默流实测：20s/40s 收到 waiting、45s 按空闲超时返回、**30s 处不再断线**。
- **日志必须按尝试记**：旧口径重试 3 次但只在开头和结尾各写一行，4–6 分钟静默与死机无法区分。现在每次失败都记「第 N/M 次、原因、用时、下次重试间隔」，流式首块与每 15s 的字符数也进日志，最终失败带总尝试次数与总耗时。
- 复现要点：`curl` 探端点只能验证可达性/认证层；真实生成是否卡住要在浏览器网络面板或带 Key 的请求里看首字节。`x-opencode-log-id` 只在网关返回响应头时才有，纯超时拿不到。
- **验证方式**：无头 Edge 149 + 临时 profile + 未打包扩展端到端跑通——真实端口用假 Key 请求网关得到 `done {status:401, logId}`；再用 CDP 把后台 `fetch` 临时替换成 SSE 假流，正常流收到 `progress(first, chars:1, 128ms)` 与 `done {ok:true, content:"你好，世界"}`，推理流收到 `stream → thinking(6 字符) → first → done`，静默流收到 20s/40s 的 waiting 与 45s 的 idle 错误，说明 SSE 解析、推理识别、端口回传、worker 保活与超时链路都通。

### 10.9 函数题协议实测（2026-10-28，v0.11.5）

用户提供新题集「算法设计与分析--课堂练习2-3」（`/problem-sets/2100000000000000021/exam/…`），题型页 `type/6` 侧栏显示**「函数题 0/2」**——不是已支持的 PROGRAMMING，而是 PTA 的函数题。IAB 实测（登录态，题型允许提交一题，已用于端到端验证）：

- **侧栏名 ≠ 协议名**：`problem-summaries` 返回 `{"CODE_COMPLETION": {total: 2, totalScore: 40}}`，页面 bundle 的分支判断也全是 `CODE_COMPLETION`——PTA 把函数题归在 CODE_COMPLETION 名下（与「程序填空」同族），侧栏才叫「函数题」。`TYPE_BY_NAME` 按侧栏名映射，`'函数题' → 'CODE_COMPLETION'`。
- **页面与编程题完全同构**：同一 `CodingProblemAnswerForm` 表单、一个可编辑 `.cm-content`、react-select 语言（显示 `C (gcc)`）、`main` 里文案为「提交本题作答」的按钮。题型只能靠题面小节判别：函数题有 `<h3>函数接口定义：</h3>` 与「裁判测试程序样例：」（模板含 `/* 你编写的函数嵌套在这里 */` 占位），编程题没有。
- **草稿信封差异（bundle 实证）**：`"CODE_COMPLETION"===a ? {codeCompletionSubmissionDetail:{program:s}} : {programmingSubmissionDetail:{program:s,compiler:u}}`——**函数题 detail 没有 compiler 字段**；另一处取值代码 `{answer: draft.codeCompletionSubmissionDetail.program, compiler: problem.compiler}` 说明提交/判题用的编译器由**题目本身**决定，语言下拉实际不可选。customTestData 形状与编程题相同。
- **端到端验证（6-1 找出次品乒乓球，接口 `int FindPingpang ( double p[], int m )`）**：POST exam-draft（detail = `{problemId:'0', problemSetProblemId, customTestData:null, codeCompletionSubmissionDetail:{program}}`）→ 200，GET 读回 detail 原样带回（customTestData 为 null 时被服务端省略，无碍）；种 `codingProblem_<id>` 水合键（形状同编程题）→ 整页 reload（`performance.timeOrigin` 变化证实真导航）→ 编辑器回带代码、按钮解锁 → 点「提交本题作答」→ exam-submissions 发出 → 提交列表显示**「答案正确 30」**（C (gcc)，1252 KB，19 ms），侧栏作答度变「函数题 1/2」。全链与编程题 relay 的实现协议一致，仅 detail 字段不同。
- **判题模板的含义**：模型只应输出**要嵌进占位处的函数实现**（签名与「函数接口定义」完全一致、可带辅助函数与必要 `#include`、禁止 main/重复裁判程序）——若输出完整程序会与模板里的 `main` 重定义。buildPrompt 的 CODE_COMPLETION 分支按此写，且不出现任何 JSON 指令（防模型输出 `{"answer":…}`）。
- **引擎侧承接**：语言一致性守卫对函数题跳过（草稿无 compiler 字段、编译器题目固定，无错配可能）；`cfg.language` 只作用于编程题；续跑单 hint 带 kind（旧单缺 kind 按编程题，向后兼容）。
