# 发版流程（维护者）

推送 `v*` 形式的 tag 即自动发版（[.github/workflows/release.yml](../.github/workflows/release.yml)），无需手动打包：

1. 确认 `extension/manifest.json` 的 `version` 已改成本次版本号（与 tag 不一致时流水线直接报错退出）；
2. 打**附注 tag** 并推送：

   ```bash
   git tag -a v0.8.0 -m "v0.8.0：一句话标题" -m "详细更新说明"
   git push origin v0.8.0
   ```

3. Actions 自动把 `extension/` 打成 `better-pta-problems-v0.8.0.zip`（zip 内为一个目录，解压后可直接「加载已解压的扩展程序」）并发布 GitHub Release，**Release 标题/正文 = 附注 tag 的信息**。轻量 tag 没有 tag 信息，此时回退为自动生成的说明。

打包前的两道校验：tag 与 `manifest.json` 的 version 一致、`extension/` 产物与 `src/` 源码一致（与 [check.yml](../.github/workflows/check.yml) 的漂移守卫同源）——所以本地改完 `src/` 要记得 `npm run build` 并把产物一并提交。

tag 打错想重发：删远端 tag 后重打重推（`git push origin :refs/tags/v0.8.0`），或在 Actions 页用 workflow_dispatch 手动填 tag 重跑（Release 已存在时会失败，需先删 Release）。

每次发版的用户可读更新说明登记在[《路线图》](./路线图.md) 的版本表里，发版时同步补一行。
