# 发版流程（维护者）

推送 `v*` 形式的 tag 即自动发版（[.github/workflows/release.yml](../.github/workflows/release.yml)），无需手动打包：

1. 确认 `extension/manifest.json` 的 `version` 已改成本次版本号（与 tag 不一致时流水线直接报错退出）；
2. 打**附注 tag** 并推送：

   ```bash
   git tag -a v0.8.0 -m "v0.8.0：一句话标题" -m "详细更新说明"
   git push origin v0.8.0
   ```

3. Actions 运行 `npm run package -- --tag <tag>` 打出 `dist/better-pta-problems-<tag>.zip` 并发布 GitHub Release，**Release 标题 = tag（如 v0.8.0，即版本号），正文 = 附注 tag 的信息**，正文结尾由流水线自动追加一段「怎么安装」提示（轻量 tag 没有 tag 信息时正文回退为一行说明，安装提示照常追加）。

## 发行 zip 的内容

```
better-pta-problems-v0.9.6/
├── extension/          ← 用户「加载已解压的扩展程序」要选的就是这个目录
└── 安装教程.html       ← 由 docs/安装教程.md 渲染（正文只维护 Markdown 一份）
```

打包由 [tools/package.mjs](../tools/package.mjs) 组装、[tools/zip.mjs](../tools/zip.mjs) 写 zip：条目名显式带 UTF-8 标志位（中文文件名在中文 Windows 的资源管理器里不会乱码），时间戳固定为 1980-01-01（同输入同字节）；打完回读中央目录自检条目齐全、标志位与 CRC 正确。

## 本地预览发行包

```bash
npm run package                  # 版本号取自 extension/manifest.json
npm run package -- --tag v0.9.6  # 顺带校验 tag 与 manifest 版本一致（与流水线同款）
```

产出在 `dist/`（已进 `.gitignore`）：组装目录 `dist/better-pta-problems-v<版本>/` 与同名 zip。想验证「用户拿到手的体验」，解开 zip 双击 `安装教程.html`、再按它把 `extension` 子文件夹加载一遍即可。

## 打包前的三道校验

- tag 与 `extension/manifest.json` 的 version 一致；
- `extension/` 产物与 `src/` 源码一致（与 [check.yml](../.github/workflows/check.yml) 的漂移守卫同源，那里还会额外跑一次打包冒烟）——所以本地改完 `src/` 要记得 `npm run build` 并把产物一并提交；
- 发行包内必须同时有 `extension/manifest.json` 与 `安装教程.html`，且包内版本等于 tag。

## 改教程 / 改包结构

- 教程正文只改 `docs/安装教程.md`（打包时渲染成 `安装教程.html`，页眉注入版本号与打包日期）；教程里引用的本地图片会被 base64 内联进 HTML，保证离线可读、单独拖出来也不裂图。
- 包结构、zip 写法改动见 `tools/package.mjs` / `tools/zip.mjs`，改完跑 `npm test`——`test/package.test.js` 钉住了目录结构、UTF-8 标志位与教程渲染。

## tag 打错想重发

删远端 tag 后重打重推（`git push origin :refs/tags/v0.8.0`），或在 Actions 页用 workflow_dispatch 手动填 tag 重跑（Release 已存在时会失败，需先删 Release）。

每次发版的用户可读更新说明登记在[《路线图》](./路线图.md) 的版本表里，发版时同步补一行。
